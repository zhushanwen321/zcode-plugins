# zac-usage — 上下文用量自查与压缩引导

收到 [z-auto-compact] 越档提醒后按本文自查读数并决定行动。核心原则：**提醒是数据投递，不是必须执行的指令**。

## 1. 何时自查

- 刚收到 [z-auto-compact] 注入的用量提醒（提醒随本轮请求可见，可先按其数字行动，也可复查最新读数）。
- 长任务各阶段主动补盲：自动检测点只在用户提交 prompt 的时刻，单次长 turn 进行中不会有任何检查——建议每个主要阶段完成后自查一次，避免长 turn 中途逼近窗口上限而无感知。

## 2. 怎么查

- 首选：直接复制运行提醒文案里内联的命令行（形如 `node /abs/path/to/z-auto-compact/bin/zac.js usage`，路径是 hook 运行时生成的真实绝对路径，可直接执行）。
- 也可显式指定会话：`node <z-auto-compact 插件根>/bin/zac.js usage --session <sessionId>`（sessionId 在提醒文案里）。
- agent 的 Bash 环境没有 sessionId 环境变量；默认 `--latest` 按 cwd 反查当前项目最近活跃主会话，在项目目录下直接跑即可，无需显式传 id。

## 3. 怎么解读（stdout 单行 JSON）

- `sessionId`：当前会话 id。
- `contextTokens`：上一轮已完成模型请求的上下文规模（input + cache_read 之和，单位 token）。`null` = 会话尚无已完成请求（首轮进行中，属正常态）。
- `firedTiers`：本压缩周期内已提醒过的档位（每档只提醒一次，压缩发生后清空重计）。
- `nextTier`：下一个高于当前用量且未提醒的档位；`null` = 已无更高档或全部档位已提醒。
- `note`：查询方式说明。

## 4. 怎么行动（数据不是指令）

三条件自查，**全部满足**才建议用户压缩：

1. 当前任务阶段已完成并验证过（不是任务中途）；
2. 后续工作不依赖将被压缩掉的细节（关键结论已写入文件或可重新获取）；
3. 用量确实构成压力（已越档且仍在增长，继续下去将很快逼近窗口上限）。

满足时，在回复中给出量化说明（当前用量、已越档位）+ 用户可直接执行的压缩建议，格式示例：

> 建议执行：/compact 保留 xxx 模块的测试清单与失败原因结论、当前方案的决定与理由

任一条不满足：忽略提醒，继续当前工作，不要为复述用量打断用户。

**本插件没有任何自行执行压缩的通道，也不要尝试构造**——最终动作只是向用户输出 `/compact <保留建议>`，由用户决定执行，或等内建 auto-compact 兜底。

## 5. 边界

- turn 进行中无自动检查点（检测点 = 用户提交 prompt 时）；长任务盲区靠第 1 节的主动自查补盲。
- 压缩（或 /rewind、/fork 回退）发生后，下一次用户 prompt 会收到「用量显著回落」知情通知——早前细节可能已被摘要，引用前先与用户确认或重读相关文件。
